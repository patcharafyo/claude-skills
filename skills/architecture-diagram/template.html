How LLM Harness fits together

A message starts in the browser, runs through a harness inside Azure App Service, reaches the models through LiteLLM, and runs code on a separate Azure VM.

The whole system

Inside the harness: how each CLI connects

The CLIs think and choose the next step, but the application makes every outside call for them.

Rules this layout enforces

  • The CLIs hold no gateway key. They get only a token for the local bridge, and it lasts for that run.
  • The CLIs' own tools are off. Their shell, file and web tools are disabled or denied, so all tool use goes through tool dispatch.
  • Generated code is kept apart from the app. Project containers run as a non-root user with no Harness login, LLM keys, Docker socket or Azure identity. They can't reach private networks or other containers, but they can download public packages. They share the VM's kernel, so this isn't VM-level isolation.
  • Only one copy of the app can run. It takes an exclusive lock on the database, and the task queue and project environments have one controller.
